# Project review rubric

Review the software milestone, not a trainee. This is not clinical validation,
protocol scoring or certification. Use the [current demo](../presentations/final-demo-run-of-show.md)
and [evidence ledger](../current-status.md).

| Area | Evidence to inspect | Open question |
| --- | --- | --- |
| Natural-language planning | Actual hosted plan, assumptions and complete seeded layouts | Does the interpretation match the brief? |
| Room preparation | Saved Blender result and accepted Unreal maps/observations | Are the whole rooms inspectable and consistent? |
| New furniture | Description/reference lineage, saved dispatch and actual returned model | Are request, job, result and review states clear? |
| Blender MCP | Preserved source, geometry/material checks, dimensions, collision fit and exported package | What still needs human correction? |
| Engine acceptance | Actual material/size/hull/cooking/contact evidence | Does the generic importer work on the real couch? |
| Review usefulness | Session replay, action timeline, findings and discussion summary | Can an instructor understand what happened? |
| Recovery | Same-dispatch reconnect, explicit retries and preserved evidence | Does failure avoid hidden spending or false completion? |
| Scope honesty | Clear fixture/live/unverified labels | Is any visual or count implying unsupported validity? |
| Security/data | Loopback, private credentials, bounded tools and sanitized evidence | What must change before deployment or real data? |

Use qualitative findings such as not shown, needs work, sufficient for this POC
and strong enough to guide the next decision. Avoid an invented overall completion
percentage. Note exact artifact/revision and who reviewed it.

Current acceptance gaps: first automated couch/SDXL run, generic engine import and
collision cooking, first live recording, then mixed-furniture room integration.
Domain-reviewed content, sensing, adaptation and deployment require separate work.
